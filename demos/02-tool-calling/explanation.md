# 02-tool-calling, explained

This is a guided walkthrough of the two source files in this demo,
[`Tools.cs`](Tools.cs) and [`Program.cs`](Program.cs), and of the Strata
features they use. For a shorter summary, see [`README.md`](README.md).

## The big picture in one paragraph

The program adds two numbers, `3 + 5`. It doesn't do the addition directly.
It calls a **tool** named `"add"` **by name**, with its arguments passed as a
**JSON string**, and reads the answer back out of a JSON string. An AI agent
works the same way: an LLM replies with "call tool `add` with
`{"a":3,"b":5}`", and the program has to turn that text into a real method
call. Strata's job is to make that step safe and fast. At compile time it
generates the code that maps the name `"add"` to the C# method `AddAsync`, so
nothing has to be looked up at runtime. Along with the JSON arguments, the
node passes a **context** that says who is calling: which thread, which node,
which attempt. The tool gets that context as an ordinary parameter.

```
 Program.cs                         generated by Strata                    Tools.cs
 ─────────                          ───────────────────                    ────────
 async graph node "Add"
   │  "add", {"a":3,"b":5},
   │  ToolCallContext.From(ctx), ct
   └──────────────► DispatchToolAsync ── switch "add" ──► AddAsync(3, 5, context)
                          │                                   │
   ◄──────────────────────┘◄──────── {"result":8} ◄───────────┘
   state.Sum = 8
```

## File 1: `Tools.cs`, defining the tool

```csharp
using Datalium.Strata.Tools;

namespace Datalium.Strata.Demos.ToolCalling;

public partial class CalculatorTools
{
    [StrataTool(Name = "add", Description = "Adds two numbers and returns their sum.")]
    public static async Task<double> AddAsync(double a, double b, ToolCallContext context)
    {
        if (context.ThreadId is null || context.NodePath is null)
        {
            throw new InvalidOperationException("add needs a caller: dispatch it with a ToolCallContext");
        }

        Console.WriteLine($"[add] called by node '{context.NodePath}' on thread '{context.ThreadId}', attempt {context.Attempt}");
        return await Task.FromResult(a + b);
    }
}
```

Line by line:

| Code | What it means |
|---|---|
| `using Datalium.Strata.Tools;` | Imports the namespace that holds `StrataToolAttribute`, `IStrataToolProvider` and `ToolCallContext`. |
| `public partial class CalculatorTools` | A normal class marked **`partial`**, which means its code can be split across several files. That matters here because Strata's source generator writes the *other half* of this class (see below). If you remove `partial`, the build fails with error **`STRATA001`**. |
| `[StrataTool(Name = "add", Description = "...")]` | Marks the method as a tool. **`Name`** is the string callers use to invoke it (`"add"`, not `"AddAsync"`). **`Description`** is the text an LLM would read to decide when to call the tool. Both are `required` on the attribute. Two tools with the same `Name` in one class fail the build with **`STRATA003`**. |
| `double a, double b` | The tool's **input fields**. Their C# types map to JSON-Schema types (`double` → `"number"`). |
| `ToolCallContext context` | **Not** an input field. The generator recognizes this type, leaves it out of the manifest, and passes in whatever context the caller gave `DispatchToolAsync`. A `CancellationToken` parameter is treated the same way. Either may sit in any position. |
| the `if (... is null)` check | The tool writes an audit line, so it needs to know its caller. A call through the two-argument `DispatchToolAsync` gets `ToolCallContext.None`, where every field is `null`, and is refused. |
| `Console.WriteLine(...)` | The audit line, built from the context: the calling node's path, the thread id, and the attempt number. |
| `return await Task.FromResult(a + b)` | The work. The demo makes it `async` on purpose, to show that the generator handles `Task<T>` returns by `await`ing them. A real tool might call a database or HTTP API here. Its **return value** becomes the tool's output. |

### Which parameter types are allowed?

The generator only accepts types it can describe in JSON Schema, plus the two
plumbing types:

| C# type | JSON-Schema type |
|---|---|
| `string` | `"string"` |
| `bool` | `"boolean"` |
| `int`, `long`, `short`, `byte` (and unsigned versions) | `"integer"` |
| `double`, `float`, `decimal` | `"number"` |
| `ToolCallContext`, `CancellationToken` | none: left out of the manifest, supplied by the dispatch call |

Any other type, such as a custom class or a `List<T>`, fails the build with
error **`STRATA002`**. A parameter that is nullable (`double?`) or has a
default value (`double b = 0`) is treated as **optional**. Every other JSON
parameter is **required**.

### Which return types are allowed?

Any of them. The generator checks the return type and picks how to call the
method:

| Return type | What the generated code does | JSON returned |
|---|---|---|
| `Task<T>` / `ValueTask<T>` (this demo) | `var result = await Method(...)` | `{"result": <value>}` |
| `T` (synchronous) | `var result = Method(...)` | `{"result": <value>}` |
| `Task` / `ValueTask` | `await Method(...)` | `{}` |
| `void` | `Method(...)` | `{}` |

## The hidden third file: what the source generator writes

You won't find this file in the repo. The compiler generates it during every
build. Here is the real output for this demo (captured with
`-p:EmitCompilerGeneratedFiles=true`):

```csharp
// <auto-generated/>
#nullable enable

namespace Datalium.Strata.Demos.ToolCalling;

partial class CalculatorTools : global::Datalium.Strata.Tools.IStrataToolProvider
{
    public string GetToolsManifest() => "[{\"name\":\"add\",\"description\":\"Adds two numbers and returns their sum.\",\"parameters\":{\"type\":\"object\",\"properties\":{\"a\":{\"type\":\"number\"},\"b\":{\"type\":\"number\"}},\"required\":[\"a\",\"b\"]}}]";

    public Task<string> DispatchToolAsync(string toolName, string jsonArguments) =>
        DispatchToolAsync(toolName, jsonArguments, ToolCallContext.None, default);

    public async Task<string> DispatchToolAsync(
        string toolName,
        string jsonArguments,
        ToolCallContext context,
        CancellationToken cancellationToken = default)
    {
        switch (toolName)
        {
            case "add":
            {
                var args = JsonSerializer.Deserialize<AddAsyncStrataArgs>(jsonArguments)
                    ?? throw new ArgumentException("Missing arguments for tool 'add'.");
                var result = await AddAsync(args.a, args.b, context);
                return JsonSerializer.Serialize(new { result });
            }
            default:
                throw new ToolNotFoundException(toolName);
        }
    }

    private sealed record AddAsyncStrataArgs(double a, double b);
}
```

*(Namespaces shortened for readability.)*

This is the core idea of the demo. The generator added four things to
`CalculatorTools`:

1. **`: IStrataToolProvider`**: the class now implements Strata's tool
   interface. That's why `Program.cs` can call `DispatchToolAsync` on a class
   that, in your source, has only one method.
2. **`GetToolsManifest()`**: returns a JSON array that describes every tool,
   with its name, description, and parameter schema. Pretty-printed:
   ```json
   [{
     "name": "add",
     "description": "Adds two numbers and returns their sum.",
     "parameters": {
       "type": "object",
       "properties": { "a": { "type": "number" }, "b": { "type": "number" } },
       "required": ["a", "b"]
     }
   }]
   ```
   This is the format LLM tool-calling APIs expect. Note that `context` is
   not in it: a model can't fill in who is calling. `Program.cs` checks
   this at the end of the run. Demo
   [`03-llm-tool-calling`](../03-llm-tool-calling) sends a manifest like
   this to a real LLM.
3. **The four-argument `DispatchToolAsync(toolName, jsonArguments, context, cancellationToken)`**:
   a plain `switch` statement. It (a) deserializes the JSON into a small
   generated record `AddAsyncStrataArgs`, which holds only the JSON
   parameters, (b) calls `AddAsync` directly, handing it `context` for the
   `ToolCallContext` parameter, and (c) wraps the answer as
   `{"result": ...}`. An unknown tool name throws `ToolNotFoundException`.
   `AddAsync` doesn't declare a `CancellationToken`, so the token isn't
   passed on. A tool that declares one gets it.
4. **The two-argument `DispatchToolAsync(toolName, jsonArguments)`**: the
   original entry point, kept for callers that have no context. It forwards
   to the four-argument one with `ToolCallContext.None`, which is why
   `AddAsync` refuses a call made through it.

### Why generate code instead of using reflection?

The usual alternative is to find methods at runtime with
`System.Reflection`. Generating the code instead has three advantages:

- **No schema drift.** The manifest and the dispatch code both come from the
  same method signature on every build. If you rename `b` to `y`, the
  manifest changes along with it. You can't advertise one shape to the LLM
  while the code expects another.
- **Errors at compile time.** A missing `partial` keyword, an unsupported
  parameter type or a duplicate tool name fails the build (`STRATA001` /
  `STRATA002` / `STRATA003`), so you find out before the program runs.
- **No reflection.** Every `case` names its target method in plain code, which
  makes it faster, easy to trim or AOT-compile, and readable (you can see the
  `switch` above).

## File 2: `Program.cs`, using the tool inside a graph

### Step 1: create the tool provider

```csharp
var toolProvider = new CalculatorTools();
```

An ordinary instance of the class. Because of the generated half, it is an
`IStrataToolProvider`.

### Step 2: build a graph with one async node

```csharp
var graph = new StateGraph<CalculatorState>()
    .AddNode("Add", async (state, ctx, ct) =>
    {
        var argsJson = JsonSerializer.Serialize(new { a = state.A, b = state.B });
        var resultJson = await toolProvider.DispatchToolAsync("add", argsJson, ToolCallContext.From(ctx), ct);
        var sum = JsonDocument.Parse(resultJson).RootElement.GetProperty("result").GetDouble();
        return state with { Sum = sum };
    })
    .Compile();
```

- **`StateGraph<CalculatorState>`**: Strata's graph builder. A graph is a set
  of **nodes** (steps) joined by **edges** (what runs next). Each node takes
  the current **state** and returns a new one. Here the state type is
  `CalculatorState`.
- **`.AddNode("Add", async (state, ctx, ct) => { ... })`**: adds a node named
  `"Add"` with an **async handler**. Demo
  [`01-hello-agent`](../01-hello-agent) used the sync form,
  `Func<TState, TState>`. This one is
  `Func<TState, NodeContext, CancellationToken, ValueTask<TState>>`, so the
  node can `await` the tool instead of blocking a thread on it. The first
  node you add automatically becomes the **entry point**. The graph has no
  edges, so `"Add"` is also the **last** node.
  - **`ctx`** is the node's `NodeContext`: the thread id, the node's path,
    the attempt number, the run id and metadata, the span, and the run's
    services.
  - **`ct`** is the run's `CancellationToken`.
- Inside the node, there are four steps:
  1. **Build the arguments as JSON.** `new { a = state.A, b = state.B }`
     becomes `{"a":3,"b":5}`. The property names must match the method's
     parameter names exactly, `a` and `b` in lowercase, because
     `System.Text.Json` is case-sensitive by default. If you wrote `A = ...`,
     the generated record would get `0` for both values.
  2. **Dispatch by name, with a context.** `ToolCallContext.From(ctx)` copies
     what the node knows (thread, run, node path, attempt, metadata, span,
     services) into a `ToolCallContext`. `DispatchToolAsync("add", argsJson,
     context, ct)` runs the generated `switch`, which calls
     `AddAsync(3, 5, context)` and returns `{"result":8}`. The tool prints
     `[add] called by node 'Add' on thread 'calc-thread', attempt 1`.
     `ToolCallContext` is a record, so a caller can add what the node
     doesn't know: `ToolCallContext.From(ctx) with { CallerId = "calculator-agent" }`.
  3. **Unwrap the result.** Read the `"result"` property out of the returned
     JSON. The value is `8`.
  4. **Return a new state.** `state with { Sum = sum }` copies the record and
     changes only `Sum`. Nodes never mutate state in place. They return a new
     version of it.
- **`.Compile()`**: validates the graph's structure (STRATA-SPEC-004), for
  example checking for orphan nodes and unguarded cycles, and returns a
  runnable `CompiledGraph<CalculatorState>`. An invalid graph makes
  `Compile()` **throw** a `GraphCompilationException`. It does not return an
  error value.

### Step 3: run it

```csharp
ICheckpointStore store = new InMemoryCheckpointStore();
var result = await graph.RunAsync("calc-thread", new CalculatorState { A = 3, B = 5 }, store);
```

- **`InMemoryCheckpointStore`** (from `Datalium.Strata.Storage`): a
  dictionary in memory where Strata saves **checkpoints**, which are
  snapshots of a paused or failed run. `RunAsync` always requires a store.
  This demo has no pause points and nothing can fail, so nothing is written
  to it. It's there because the API needs it. Demo
  [`05-hitl-interruption`](../05-hitl-interruption) is where checkpoints
  matter.
- **`RunAsync(threadId, initialState, store)`**: runs the graph from its
  entry point.
  - `"calc-thread"` is the **thread id**. It names this run so a paused run
    could be found and resumed later. It is also what `ctx.ThreadId`, and so
    the tool's `context.ThreadId`, reports.
  - `new CalculatorState { A = 3, B = 5 }` is the starting state.
  - An optional last argument is a `CancellationToken`. This demo doesn't
    pass one, so `ct` in the node never fires.

### Step 4: handle the result

```csharp
switch (result)
{
    case GraphExecutionResult<CalculatorState>.Completed completed:
        Console.WriteLine($"{completed.State.A} + {completed.State.B} = {completed.State.Sum}");
        Check(completed.State.Sum == 8, "the tool's sum came back into the state");
        break;
    case GraphExecutionResult<CalculatorState>.Failed failed:
        throw new InvalidOperationException($"graph execution failed: {failed.Message}");
    default:
        throw new InvalidOperationException($"unexpected result: {result}");
}
```

`RunAsync` returns a `GraphExecutionResult<TState>`. It doesn't throw for
routine outcomes. These are the cases:

| Case | Meaning | In this demo |
|---|---|---|
| `Completed(State)` | The graph reached its end. | ✅ This is what happens. It prints `3 + 5 = 8`. |
| `Failed(Message)` | Something went wrong, such as no edge condition matching. `NodeFailed` and `HopLimitExceeded` are more specific subtypes. | Shouldn't happen. |
| `Interrupted(...)` | The run paused at an **interrupt boundary** or a wait, to resume later. | Can't happen: there's no boundary or wait. |
| `Cancelled(...)` | The run's token fired or its deadline passed. | Can't happen: no token is passed. |

An exception thrown by the tool (say, the "needs a caller" refusal) is not
turned into `Failed`. It propagates out of the plain node and out of
`RunAsync`. Turning failures into results and retries takes fallible nodes,
covered in [`08-error-recovery`](../08-error-recovery).

`Check(...)` is a small helper at the bottom of the file: it prints the claim
and exits with code 1 if the condition is false, so the demo can't drift
silently.

### Step 5: check the manifest

```csharp
var parameters = JsonDocument.Parse(toolProvider.GetToolsManifest()).RootElement[0].GetProperty("parameters");
var names = parameters.GetProperty("properties").EnumerateObject().Select(p => p.Name).ToList();
Console.WriteLine($"manifest parameters for 'add': {string.Join(", ", names)}");
Check(names.SequenceEqual(["a", "b"]), "the ToolCallContext parameter is left out of the manifest");
```

The manifest is what a model would be shown. `AddAsync` has three
parameters, but only `a` and `b` are arguments a model fills in, so those are
the only two listed.

### Step 6: the state type

```csharp
sealed record CalculatorState
{
    public required double A { get; init; }
    public required double B { get; init; }
    public double? Sum { get; init; }
}
```

- A **`record`**: an immutable data type that supports `with` copies. That
  fits Strata's model, where each node returns a new state.
- `A` and `B` are **`required`** inputs. `Sum` is **nullable** (`double?`)
  because it's empty until the `"Add"` node fills it in.
- State should be plain data that can be serialized to JSON. When Strata
  checkpoints a run, it serializes the state with `System.Text.Json`.

## The project file: `02-tool-calling.csproj`

The demo is built from two of Strata's NuGet packages:

```xml
<PackageReference Include="Datalium.Strata" />
<PackageReference Include="Datalium.Strata.Storage" />
```

| Reference | Provides |
|---|---|
| `Datalium.Strata` | `StateGraph`, `CompiledGraph`, `NodeContext`, `GraphExecutionResult`, `ICheckpointStore`, `[StrataTool]`, `IStrataToolProvider`, `ToolCallContext` |
| `Datalium.Strata.Storage` | `InMemoryCheckpointStore` |
| `Datalium.Strata.SourceGenerators` | The code generator that writes the hidden file above. It is not a package of its own: it ships inside `Datalium.Strata`, in the package's `analyzers/dotnet/cs` folder |

**The gotcha:** the generator runs because this project references
`Datalium.Strata` **directly**. NuGet hands a package's analyzers to the
project that references it, but not on to projects that reference *that*
project. So if your tools live in a class library and only the app
references `Datalium.Strata`, nothing generates the other half of
`CalculatorTools`, and the build fails because `DispatchToolAsync` doesn't
exist. Reference `Datalium.Strata` from the project that declares the tools.
The version comes from the repo's shared `Directory.Packages.props`.

## Strata features used, at a glance

| Feature | Spec | Where it's used |
|---|---|---|
| `[StrataTool]` attribute | STRATA-SPEC-003 | `Tools.cs`: marks `AddAsync` as a tool named `"add"` |
| Source generator (`Datalium.Strata.SourceGenerators`) | STRATA-SPEC-003 | Writes the second half of `CalculatorTools` at build time |
| `IStrataToolProvider.GetToolsManifest()` | STRATA-SPEC-003 | `Program.cs`: checked to list only `a` and `b` |
| Four-argument `IStrataToolProvider.DispatchToolAsync()` | design/20 | `Program.cs`: the `"Add"` node calls the tool by name, with a context and token |
| `ToolCallContext` / `ToolCallContext.From(NodeContext)` | design/20 | Built in the node, received as a parameter by `AddAsync` |
| `ToolNotFoundException` | STRATA-SPEC-003 | Thrown by the generated `default:` case for unknown names |
| Build errors `STRATA001` / `STRATA002` / `STRATA003` | STRATA-SPEC-003 | Not triggered; they guard against a non-`partial` class, bad parameter types, a duplicate tool name |
| `StateGraph<TState>` + async `AddNode` | Core graph / design/17 | Builds the one-node graph; the handler gets `NodeContext` and a token |
| `Compile()` with validation | STRATA-SPEC-004 | Checks the graph's structure before it can run |
| `CompiledGraph.RunAsync` | Core graph | Runs the graph from its entry point |
| `GraphExecutionResult` | STRATA-SPEC-002 | `Program.cs`'s `switch` over the outcome |
| `ICheckpointStore` / `InMemoryCheckpointStore` | STRATA-SPEC-002 | Required by `RunAsync`; unused here because nothing pauses or fails |

## What this demo deliberately does *not* do

- **No LLM.** The arguments `{"a":3,"b":5}` come from the graph's own state.
  In a real agent they would come from an LLM's tool-call reply, which is
  what [`03-llm-tool-calling`](../03-llm-tool-calling) shows;
  [`23-agent-tool-loop`](../23-agent-tool-loop) runs the full agent loop.
- **No `ToolRegistry`.** The node calls the generated provider directly. A
  registry combines several providers, gives each agent a curated subset,
  runs middleware around every call, and traces each call with a span and
  run events; see
  [`26-tool-registry-and-middleware`](../26-tool-registry-and-middleware).
- **No edges, branching, interrupts, streaming, retries or cancellation.** One
  node, one tool call, one result. Later demos add these one at a time.

## Try it yourself

```bash
dotnet run --project demos/02-tool-calling/02-tool-calling.csproj
# [add] called by node 'Add' on thread 'calc-thread', attempt 1
# 3 + 5 = 8
# manifest parameters for 'add': a, b
```

Some experiments that show the features working:

1. **Remove `partial`** from `CalculatorTools`. The build fails with
   `STRATA001`.
2. **Change a parameter to `List<int>`**. The build fails with `STRATA002`.
3. **Add a second `[StrataTool(Name = "add", ...)]` method**. The build fails
   with `STRATA003`.
4. **Call `DispatchToolAsync("subtract", ...)`**. The run throws
   `ToolNotFoundException: Tool 'subtract' was not found.`
5. **Drop the context**: call the two-argument
   `DispatchToolAsync("add", argsJson)`. The tool gets `ToolCallContext.None`
   and the run throws `add needs a caller: dispatch it with a ToolCallContext`.
6. **Pass a caller id**: `ToolCallContext.From(ctx) with { CallerId = "calculator-agent" }`,
   and print `context.CallerId` in the tool.
7. **See the generated file** by building with
   `-p:EmitCompilerGeneratedFiles=true` and looking under `obj/` for
   `CalculatorTools.StrataTools.g.cs`.
